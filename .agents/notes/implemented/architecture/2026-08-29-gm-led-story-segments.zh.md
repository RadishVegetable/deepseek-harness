# Agent Note: GM-led story segments

Status: implemented

[English](2026-08-29-gm-led-story-segments.md) | 中文

## 问题

互动式 Tavern 故事不是一串彼此孤立的角色回复。一次玩家输入可能需要在同一个连贯续写中包含环境正文、多个角色的行动、对白和新的情境。为每个角色分别调用模型会重复上下文，把 token 花在协调上，也会错误地让角色看起来像模型的对话对象。

## 决策

Tavern 的每个 Journey 都使用一条 GM 叙事循环。模型接收所选角色卡 baseline、附属和选中的世界书、Journey 历史以及当前 Journey 上下文。一次玩家输入只产生一次模型生成和一条 assistant 响应；响应可以包含旁白、环境变化以及任意可见角色的行动或对白。

GM 响应协议包含完整的 `story` 正文和可选的 `updates` 封套。`updates.people[personId]` 和 `updates.world` 包含自然语言的 `add`、`replace` 和 `remove` 操作。Host 接受 JSON 对象、fenced JSON 和普通自由文本；无法解析的响应会完整保留为 `story`。Host 先持久化 assistant 响应，再应用更新，不会再次调用模型提取事实。

Journey 事实以追加式 `tavern/fact` 事件保存，并投影为 `people[personId]` 和 `world`。Host 为追加分配 fact ID，校验人物和事实目标，记录带 assistant 序号和回合的拒绝操作，并使用响应指纹保证重试幂等。替换和撤销都会追加事件，不会抹掉原始操作。角色卡是 Journey 锚点，只有所选世界书明确识别某人为人物时才会进入人物集合。

活动 Journey 从 `tavern/assets-selected` 读取所选资源 ID，并在构建上下文时解析当前源记录。接受的事实事件提供 Journey 专属连续性，不会修改导入的角色卡或世界书来源。世界人物使用源名称生成的稳定人物 ID，最新的 `Name` 事实提供显示名，带标签的事实会投影到详情动态栏目。多个 Journey 可以引用同一来源记录，但不会共享 transcript、事实、分支或资源库编辑。浏览器把剧情段作为一条响应展示，不锁定当前发言者，也不为角色创建独立发送链路。

## 考虑过的替代方案

**为每个角色分别调用模型。** 这种方式会重复发送世界、Journey 和 Scene 上下文，并需要调度器决定顺序。一次 GM 生成可以保留因果顺序并避免协调调用。

**每回合先调用规划器，再调用角色写作者。** 两次强制调用会增加延迟，也可能让计划和正文发生偏离。规划保留为带有明确成本的可选后续能力。

**使用固定的关系和状态 schema。** 固定字段会在产品尚未知道故事需要哪些区分前，强迫所有故事使用同一套词汇。自然语言事实保留任意故事概念，操作封套则提供持久化修改语义。

**修改导入的角色卡或世界书。** 共享来源的修改会把一个 Journey 的发现泄露到另一个 Journey，并破坏作者资源。Journey 事实事件让来源保持可复用；资源库替换仍是明确的库操作，按 ID 选择的 Journey 会解析当前记录。

## 后果

常用路径每次玩家输入只发送一次模型请求，同时保留完整 assistant 正文、自动连续性更新、确定性回放和可审计的拒绝记录。提示词可以召回带来源事件序号的人物和世界事实，Prompt Inspector 可以追溯所选 baseline 和激活记录。

事实词汇保持小而稳定，不建模关系、库存、健康或类似固定字段。当前 UI 展示模型或回退方式整理的源栏目，将 Journey 事实覆盖到动态栏目，允许玩家编辑或撤销已有事实，并通过 Prompt Inspector 暴露最近请求输入和 assistant 正文。块级归属、作者编辑资源后的再次整理以及更丰富的 Journey 专属作者资源编辑仍待实现。

## 验证

Host 测试覆盖结构化和自由文本解析、每次输入一次生成、合法人物和世界更新、格式错误和越权操作、替换与撤销、审计保留、重试与 reload 幂等、分支隔离、来源不变以及下一次请求召回。客户端测试覆盖世界人物和世界书详情，以及事实编辑和撤销控件。
